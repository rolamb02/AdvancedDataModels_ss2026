01
Query Model
SPARQL – Pattern Matching statt Tabellen
SQL — Tabellen & explizite Joins
SELECT u.name, c.name
FROM university u
JOIN city c ON u.location_id = c.id
WHERE c.state = 'Baden-Württemberg'
Tabellenschema nötig
Explizite JOIN-Keys
SPARQL — Graph Pattern Matching
SELECT ?uniname ?stadtname
WHERE {
  ?u a uni:University .
  ?u rdfs:label ?uniname .
  ?u uni:location ?stadt .
  ?stadt uni:bundesland "Baden-Wuerttemberg" .
  ?stadt rdfs:label ?stadtname .
}
Kein JOIN-Keyword
Geteilte Variablen
W3C-Standard
→location_id = 42 ist eine nackte Zahl — keine Bedeutung außerhalb der DB. uni:location ist eine URI: global, maschinenlesbar, W3C-standardisiert. Das ist der Semantik-Unterschied.
02
Query Model
Query-Typen – SELECT · ASK · CONSTRUCT · DESCRIBE
SELECT — Tabelle
SELECT ?u ?name WHERE { ... }
Eine Spalte pro Variable, eine Zeile pro Match — Standardfall für alle Abfragen.
ASK — Boolean
ASK { uni:AliceSchmidt a uni:Student . }
Nur true oder false — kein Datensatz. Validierung, Assertions, Existenz-Checks.
CONSTRUCT — neuer Graph
CONSTRUCT {
  ?p foaf:name ?name ;
    foaf:memberOf uni:Stuttgart .
} WHERE {
  ?p a uni:Student ;
    uni:hatName ?name ;
    uni:studiertAn uni:Stuttgart .
}
Übersetzt uni:-Vokabular in foaf: — Quellen vereinheitlichen, RAG-Kontext aufbereiten.
DESCRIBE — Ressource
DESCRIBE uni:Stuttgart
Alles über eine URI — store-definiert, oft äquivalent zu SELECT ?p ?o WHERE { uni:Stuttgart ?p ?o }. Schnelle Exploration.
→CONSTRUCT macht RDF zum strukturierten RAG-Kontext — jede LLM-Aussage bleibt auf konkrete Triples rückführbar. ASK für automatisierte Konsistenz-Checks.
03
Query Model
Triple Patterns & SELECT / WHERE
Anatomie einer SPARQL-Query
PREFIX uni: <http://example.org/uni/>
PREFIX rdfs: <http://www.w3.org/2000/01/rdf-schema#>

SELECT ?u ?name ← Ausgabe-Variablen
WHERE {
  ?u a uni:University . ← Typ-Pattern
  ?u rdfs:label ?name . ← Attribut-Pattern
}
ORDER BY ?name
?u ist dieselbe Variable in beiden Patterns — das verbindet sie wie ein JOIN, ohne JOIN-Keyword.
Schlüsselkonzepte
Variablen mit ?
Platzhalter für beliebige Werte — Typ entsteht durch Patterns, nicht durch den Namen
Präfixe
Kurzschreibweise für Namespace-URIs
Implizites AND
Alle Patterns müssen gleichzeitig matchen — Reihenfolge egal, der Optimizer startet mit dem selektivsten Pattern (wenigste Treffer) und hält Zwischenergebnisse klein
→Präfixe sind Kürzel — keine aktive Datenbank. Typisierung entsteht durch das Pattern ?s a uni:University, nicht den Variablennamen.
04
Query Model
FILTER · OPTIONAL · Property Paths
FILTER
SELECT ?name ?sem
WHERE {
 ?s a uni:Student;
   rdfs:label ?name;
   uni:semester ?sem.
 FILTER(?sem >= 5)
}
Schränkt Bindungen ein — analog zu SQL WHERE
OPTIONAL
SELECT ?name ?fach
WHERE {
 ?p a uni:Professor;
   rdfs:label ?name.
 OPTIONAL {
  ?p uni:fach ?fach.
 }
}
= LEFT JOIN · Open World: fehlendes Triple = „unbekannt". Ohne OPTIONAL: Zeile fällt raus — 0 Treffer, kein Fehler
Property Path
-- Alt-Prädikate:
?person
 (uni:studiesAt
  | uni:worksAt) ?u .

-- Transitive:
?typ rdfs:subClassOf*
     uni:Person .
| = „oder"  ·  * = 0 oder mehr Schritte  ·  + = mind. 1 Schritt  ·  / = A dann B
Alt-Muster (ganze WHERE-Blöcke) → UNION
→OPTIONAL = LEFT JOIN · FILTER = WHERE-Bedingung · Property Paths = Graph-Traversal in einer Zeile.
05
Query Model
Aggregation – COUNT, GROUP BY, ORDER BY
Personen pro Universität zählen
SELECT ?uniname
  (COUNT(?person) AS ?anzahl)
WHERE {
  ?person a ?typ .
  ?typ rdfs:subClassOf* uni:Person .
  ?person (uni:studiesAt|uni:worksAt) ?u .
  ?u rdfs:label ?uniname .
}
GROUP BY ?uniname
ORDER BY DESC(?anzahl)
Was steckt drin?
Aggregation
COUNT(?person) zählt Personen pro Gruppe · GROUP BY ?uniname gruppiert nach Universität — Syntax wie SQL GROUP BY
rdfs:subClassOf*
Findet alle Klassen unterhalb uni:Person — braucht zusätzlich ?person a ?typ für Instanzen
→COUNT/GROUP BY wie in SQL — aber die Treffermenge entsteht durch Graph-Pattern-Matching, nicht durch Tabellen-Scans.

07
Query Model
Traversal vs. Inferenz · RDF vs. Property Graph
Traversal vs. Inferenz
Hier: Traversal entlang gespeicherter subClassOf-Kanten. Bei Inferenz/Entailment (Architecture) leitet der Store das neue Triple ab und speichert es zusätzlich.
RDF vs. Property Graph
Property Graph: Pointer-Hop ist sehr schnell, kennt Klassenhierarchien aber nicht nativ. RDF: Index-Lookup pro Schritt, gewinnt aber beim semantischen Traversal via subClassOf*.
→Dasselbe Modell, dasselbe Wissen — nur Modellwissen über Klassenhierarchien genutzt. Das ist der Unterschied zu SQL und Property Graph.
08
Query Model
Federated Queries – Das Web of Data
SERVICE — Live-Anfrage gegen DBpedia
SELECT ?uniname ?description
WHERE {
  -- lokale Daten:
  ?u a uni:University .
  ?u rdfs:label ?uniname .
  ?u owl:sameAs ?dbCity .

  -- externe Quelle:
  SERVICE <https://dbpedia.org/sparql> {
    ?dbCity dbo:abstract ?description .
    FILTER (lang(?description) = "de")
  }
}
Verknüpft lokale Daten mit externen Endpoints via owl:sameAs — kein Datenkopie nötig.
Warum geht das nur mit W3C-SPARQL?
Oxigraph, DBpedia, Wikidata, GraphDB, Neptune — alle sprechen denselben Standard
Neo4j Cypher, MongoDB: keine gemeinsame Abfragesprache mit externen Endpoints
Ein Query-Mechanismus, viele Datenquellen weltweit
Ausgabeformate
JSON (APIs, RAG) · CSV (Tabellenanalyse) · RDF/XML (CONSTRUCT-Export)
→SERVICE verbindet lokale Daten live mit dem Web of Data — keine Kopie, kein ETL, nur möglich durch W3C-Standardisierung.
