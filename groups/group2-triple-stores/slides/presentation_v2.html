Physische Speicherung I – Dictionary-Encoding
Von URIs zu Integer-IDs
Warum Dictionary-Encoding?
Schnelle Vergleiche
Integer-Vergleich statt String-Vergleich — deutlich schneller bei Millionen Triples
Kompakter Speicher
Lange URIs nur einmal im Dictionary — in der Triple Table nur IDs
Trade-off
Zusätzliche Dictionary-Verwaltung — bei Lookups ist immer ein Decode-Schritt nötig
→Dictionary-Encoding: URIs → Integer-IDs. Schnellere Vergleiche, kompakterer Speicher auf Kosten eines Lookup-Layers.

Query Model
SPARQL – Pattern Matching statt Tabellen
SQL — Tabellen & explizite Joins
SELECT u.name, c.name
FROM university u
JOIN city c ON u.location_id = c.id
WHERE c.state = 'Baden-Württemberg'
Tabellenschema nötig
Explizite JOIN-Keys
SPARQL — Graph Pattern Matching
SELECT ?uniname ?stadtname
WHERE {
  ?u a uni:University .
  ?u rdfs:label ?uniname .
  ?u uni:location ?stadt .
  ?stadt uni:bundesland "Baden-Wuerttemberg" .
  ?stadt rdfs:label ?stadtname .
}
Kein JOIN-Keyword
Geteilte Variablen
W3C-Standard
02
Query Model
Triple Patterns & SELECT / WHERE
Anatomie einer SPARQL-Query
PREFIX uni: <http://example.org/uni/>
PREFIX rdfs: <http://www.w3.org/2000/01/rdf-schema#>

SELECT ?u ?name ← Ausgabe-Variablen
WHERE {
  ?u a uni:University . ← Typ-Pattern
  ?u rdfs:label ?name . ← Attribut-Pattern
  ?u uni:location ?stadt .
  ?stadt uni:bundesland "Baden-Wuerttemberg" .
}
ORDER BY ?name
?u ist dieselbe Variable in beiden Patterns — das verbindet sie wie ein JOIN, ohne JOIN-Keyword.
Schlüsselkonzepte
Variablen mit ?
Platzhalter für beliebige Werte — Typ entsteht durch Patterns, nicht durch den Namen
Präfixe
Kurzschreibweise für Namespace-URIs
Implizites AND
Selektivstes Pattern zuerst (Optimizer)
→Präfixe sind Kürzel — keine aktive Datenbank. Typisierung entsteht durch das Pattern ?s a uni:University, nicht den Variablennamen.
03
Query Model
Query-Typen – SELECT · ASK · CONSTRUCT · DESCRIBE
SELECT — Tabelle
SELECT ?u ?name WHERE { ... }
Eine Spalte pro Variable, eine Zeile pro Match — Standardfall für alle Abfragen.
ASK — Boolean
ASK { uni:AliceSchmidt a uni:Student . }
Nur true oder false — kein Datensatz. Validierung, Existenz-Checks.
CONSTRUCT — neuer Graph
CONSTRUCT {
  ?p foaf:name ?name ;
    foaf:memberOf uni:Stuttgart .
} WHERE {
  ?p a uni:Student ;
    uni:hatName ?name ;
    uni:studiertAn uni:Stuttgart .
}
Übersetzt uni:-Vokabular in foaf: — Quellen vereinheitlichen, RAG-Kontext aufbereiten.
DESCRIBE — Ressource
DESCRIBE uni:Stuttgart
Alles über eine URI — store-definiert, oft äquivalent zu SELECT ?p ?o WHERE { uni:Stuttgart ?p ?o }. Schnelle Exploration.
→CONSTRUCT macht RDF zum strukturierten RAG-Kontext — jede LLM-Aussage bleibt auf konkrete Triples rückführbar. ASK für automatisierte Konsistenz-Checks.
04
Query Model
Aggregation – COUNT, GROUP BY, ORDER BY
Personen pro Universität zählen
SELECT ?uniname
  (COUNT(?person) AS ?anzahl)
WHERE {
  ?person uni:studiesAt ?u .
  ?u rdfs:label ?uniname .
}
GROUP BY ?uniname
ORDER BY DESC(?anzahl)
Was steckt drin?
Aggregation
COUNT(?person) zählt Personen pro Gruppe · GROUP BY ?uniname gruppiert nach Universität — Syntax wie SQL GROUP BY
→COUNT/GROUP BY wie in SQL — aber die Treffermenge entsteht durch Graph-Pattern-Matching, nicht durch Tabellen-Scans.
05
Query Model
FILTER · OPTIONAL · Property Paths
FILTER ≈ SQL WHERE
SELECT ?name ?sem
WHERE {
 ?s a uni:Student;
   rdfs:label ?name;
   uni:semester ?sem.
 FILTER(?sem >= 5)
}
Bedingung auf Ergebnisse
Schränkt bereits gebundene Variablen ein
OPTIONAL ≈ LEFT JOIN
SELECT ?name ?fach
WHERE {
 ?p a uni:Professor;
   rdfs:label ?name.
 OPTIONAL {
  ?p uni:fach ?fach.
 }
}
Optional statt Pflicht
Fehlendes Triple = „unbekannt" (Open World). Ohne OPTIONAL fällt die Zeile raus — 0 Treffer, kein Fehler.
PROPERTY PATH Graph-Traversal
-- Alternative Prädikate:
?person (uni:studiesAt
        | uni:worksAt) ?u .

-- Transitiv (0+ Schritte):
?typ rdfs:subClassOf* uni:Person .
Traversal in einer Zeile
subClassOf* = beliebig viele Hops die Hierarchie hoch — die Engine läuft sie ab, keine Schleife im Code.
| oder  ·  * 0+  ·  + ≥1  ·  / A→B
06
Query Model
Inferenz in der Praxis
Query 4 — ohne Inferenz
SELECT ?p WHERE { ?p a uni:Person . }
0
Ergebnisse
Niemand ist explizit als uni:Person gespeichert
Reasoner
aktivieren
Query 5 — mit rdfs:subClassOf*
SELECT ?p WHERE {
  ?p a ?typ .
  ?typ rdfs:subClassOf* uni:Person .
}
7
Ergebnisse
Studenten + Professoren + Staff werden erkannt
→SPARQL gibt zurück, was im Graph gilt — nicht nur, was wörtlich gespeichert ist. Alice wird über die Klassenhierarchie automatisch zur Person.
07
Query Model
Traversal vs. Inferenz · Die Klassenhierarchie dahinter
Klassenhierarchie im Datensatz
Gespeichert ist nur alice a uni:Student. Über die Kette Student → AcademicPerson → Person macht subClassOf* sie transitiv zur uni:Person
Traversal vs. Inferenz
Hier: Traversal entlang gespeicherter subClassOf-Kanten. Bei Inferenz/Entailment (Architecture) leitet der Store das neue Triple ab und speichert es zusätzlich.
→Dasselbe Modell, dasselbe Wissen — nur Modellwissen über Klassenhierarchien genutzt. Das ist der Unterschied zu SQL und Property Graph.
08
Query Model
Federated Queries – Das Web of Data
SERVICE — Live-Anfrage gegen Wikidata
SELECT ?uniname ?description
WHERE {
  -- lokale Daten:
  ?u a uni:University .
  ?u rdfs:label ?uniname .
  ?u uni:location ?wdCity .

  -- externe Quelle (live):
  SERVICE <https://query.wikidata.org/sparql> {
    VALUES ?wdCity { wd:Q1726 wd:Q64 }
    ?wdCity schema:description ?description .
    FILTER (lang(?description) = "de")
  }
}
Standort zeigt direkt auf eine globale Wikidata-URI — kein Datenkopie nötig

SPARQL = Pattern Matching
Man beschreibt ein gesuchtes Graph-Muster, woraufhin die Engine alle dazu passenden Belegungen findet (ganz ohne ausformulierte Joins).
01
Geteilte Variablen verbinden
Taucht dieselbe Variable (etwa ?u) in mehreren Patterns auf, verknüpft sie diese automatisch und wirkt damit wie ein impliziter Join.
02
Vier Ergebnisformen
Je nach Ziel liefert SPARQL eine Tabelle (SELECT), ein Ja/Nein (ASK), einen neuen Graphen (CONSTRUCT) oder alle Fakten zu einer Ressource (DESCRIBE).
03
Verfeinern & Traversieren
FILTER schränkt Ergebnisse über Bedingungen ein, OPTIONAL lässt fehlendes Wissen zu (Open World) und Property Paths traversieren den Graphen, ohne dass man Schleifen programmiert.
04
Inferenz (implizites Wissen)
SPARQL liefert nicht nur wörtlich gespeicherte Fakten, sondern auch das, was im Graph logisch gilt (etwa Unterklassen, die über die Klassenhierarchie automatisch mitgefunden werden).
05
Das Abfragen sitzt (SPARQL, Inferenz, Federation). Als Nächstes die Architecture: wie läuft das produktiv und skalierbar?

Deployment
Ein Triple Store lässt sich entweder selbst betreiben oder als fertiger Managed-Cloud-Dienst beziehen.
02
Skalierung
Replication erhöht die Verfügbarkeit (mehrere Kopien), während Sharding die Daten auf mehrere Knoten verteilt.
03
Partitionierung
Die Verteilung kann nach Subjekt, Prädikat oder zusammenhängenden Teilgraphen erfolgen, je nach erwartetem Workload.
04
Verteilte Graph-Joins
Die zentrale Herausforderung beim Sharding: Tripel sind über den ganzen Graph verflochten, sodass Joins über Knotengrenzen hinweg teuer werden.
